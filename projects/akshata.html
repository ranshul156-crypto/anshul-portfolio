Project · Nov 2025 – present

Akshata Cycle Tracker

A prototype that looked finished and had never shipped. I rebuilt it so it could.

  • Role Lead developer — forecasting engine + backend
  • Stack React · TypeScript · Firebase Auth · Firestore
  • Live akshata-cycle-tracker.web.app
  • Users Live for Akshata Foundation (NGO) — count author-reported, see Evidence page

I.

Context

Akshata Foundation works on menstrual health. When I joined, there was already a prototype — designed, demoed, and never deployed. Nobody could quite tell me why it hadn't shipped, which is usually the sign that “ship” was treated as the last step instead of the first constraint.

Auth wasn't wired. Firestore rules weren't written. The forecasting engine didn't exist. I took on all three, because a health app that only works in a presentation is not a health app. It's a picture of one.

So now I start from deployment backwards. If a feature can't survive real accounts, real rules, and real phones, I don't count it as built.

II.

Method

The forecast sees two sequences and nothing else. From the days a user marks as period days, it groups bleeds (a gap of two days or less is the same bleed) and derives cycleLengths[] — days between bleed starts — and periodLengths[]. A computed cycle is kept only if it lands between 16 and 59 days; anything outside that is dropped before the model ever sees it, because it is almost certainly a logging gap, not a cycle.

With fewer than four cycles, it does the only defensible thing: an exponentially-weighted mean, recent cycles counting more, with period length defaulting to five days. It labels itself low confidence while it does so. There isn't enough history to justify anything cleverer, and a confident wrong prediction is worse than a modest one.

From four cycles up, a per-user autoregression joins in: lag order 1–3, chosen by error on the held-out last cycle, fit by OLS and then twenty IRLS passes with Huber weights (c = 1.35) so one mistyped month can't drag the forecast with it. That prediction is blended 50/50 with the weighted mean, clamped to 21–60 days for cycle and 2–10 for period. Confidence only earns the word high at ten or more cycles, and never for an irregular history.

And then the honest part, which I verified against the deployed production bundle on 2026-10-05 rather than from memory: mood, symptoms and flow grade are logged, displayed and exported — the forecast is blind to all three. Ovulation is not modelled either; it is predicted cycle length minus fourteen, fixed arithmetic wearing a lab coat. This is a deliberately low-variance model for people who have four to eight data points, and it ignores almost everything on purpose.

So now I describe models from the code that is actually deployed, not from the version I remember building. If symptoms ever enter the forecast, that will be a real second version — and the sentence goes on this page after the code does it, not before.

Privacy pass, Oct 2026: menstrual data is sensitive data. Nothing is stored in a form the user hasn't explicitly agreed to — consent first, features second.
Technical line, for those who check: a per-user Huber-robust autoregression blended with an exponentially-weighted mean, fit on self-reported cycle and period lengths only. Not ARIMA — there is no differencing and no moving-average term, whatever the current UI label says.

III.

Failure

Day one, a real user found a bug I hadn't. I had tested the app thoroughly — as myself, on my data, in the order I expected it to be used. She used it the way people actually use things.

Nothing about that is unusual, which is exactly why it stung. “Tested by me” and “tested by a real user” turned out to be different categories, and I had been filing them under the same word.

So now anything that touches the forecasting path ships behind a feature flag, and gets watched with real usage before it reaches everyone. A wrong prediction on someone else's body is worse than no prediction at all.

IV.

What's next

First, a small naming fix that retires a real inaccuracy: the app's UI still says “ARIMA + Huber ML predictions,” and it isn't ARIMA. The label becomes Adaptive forecast (robust regression + weighted mean) — boring, and true. Anonymised, aggregate analytics after that, so the Foundation can see patterns across users without seeing any individual. And the privacy/consent pass written up as a short standalone document, so another small NGO doesn't have to reinvent it.

The goal was never to scale this as fast as possible. It's for the work to still be running, correctly, after I'm no longer the person maintaining it. So now I write the handover notes as I go, not at the end.
